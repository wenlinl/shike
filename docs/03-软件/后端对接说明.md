## 1. 架构

```text
T5-E1 固件（copy 工程 app_xzd）
  │  HTTPS multipart POST /api/scan（图片 + deviceId/action/container/timestamp/requestId + X-Device-Token 头）
  ▼
后端（食刻后端工程 · 复用其服务器/域名/火山方舟 Key）
  │  保存图片 → 火山方舟视觉模型 doubao-seed-2-1-turbo-260628 识别
  ▼
SQLite（FoodItem 当前库存 + ScanLog 流水）→ 扁平 JSON 返回固件
  │
  ▼
软件端：网页大屏 / H5 / App
  GET /api/items（库存按容器） · GET /api/reminders（临期/过期） · PATCH /api/items/[id]（改容器）
```

## 2. 接口契约

### POST /api/scan（设备 Token / 登录会话鉴权）

multipart/form-data：

| 字段 | 说明 |
|---|---|
| `image` | JPEG（640×480，30–60KB），filename=scan.jpg |
| `deviceId` | 如 `xzd-t5e1-001` |
| `action` | `in`（放入）\| `out`（取出） |
| `container` | 冰箱 \| 零食柜 \| 药盒 \| 调料柜 \| 主食柜 |
| `timestamp` | `YYYY-MM-DD HH:mm:ss`（UTC，可为空） |
| `requestId` | 幂等键（固件自动生成，网络重试不会重复入库） |

请求头：`X-Device-Token: <设备 Token>`（固件）；H5 手机扫描用登录会话 Cookie 即可。

响应（扁平 JSON，固件解析这些键）：

```json
{"code":0,"name":"光明鲜牛奶","scannedAt":"2026-08-15 23:22:00","expiryDate":"2026-08-17","daysLeft":2,"suggestedContainer":"冰箱","confidence":0.92,"note":"","keepDays":3,"stockTotal":12}
```

- `code!=0` 或 HTTP 非 200 → 固件显示“网络不好请重试”；
- `name` 为空 / `confidence<0.50` → 固件走 LOW_CONF，提示“没看清，重新对准再拍”；
- 后端自动：保存图片 → ARK 视觉识别 → 更新 FoodItem（in 加数量 / out 减数量，减到 0 删除）→ 写 ScanLog。

### GET /api/items?container=冰箱（需登录 + 家庭）

```json
{"code":0,"items":[{"id":"...","name":"光明鲜牛奶","category":"乳制品","container":"冰箱","quantity":1,"expiryDate":"2026-08-17","scannedAt":"...","daysLeft":2,"confidence":0.92,"note":"","status":"soon"}]}
```

按容器筛选、剩余天数升序；`status` = normal / soon（≤3 天）/ expired。

### PATCH /api/items/[id]（需登录 + 家庭）

```json
{"container":"零食柜"}
```

手动修改容器分类。

### GET /api/reminders（需登录 + 家庭）

```json
{"code":0,"soon":[{"id":"...","name":"...","container":"冰箱","quantity":1,"expiryDate":"2026-08-17","daysLeft":2,"suggestion":"建议尽快食用"}],"expired":[]}
```

## 3. 数据库模型（Prisma / SQLite）

- `FoodItem`：当前库存（`@@unique([name, container, deviceId])`，in 加数量 / out 减数量）；
- `ScanLog`：每次扫描流水（最近记录 / 统计）。

### 3.1 数据库需求（v3 · 按最新软件端 食刻-H5手机端.html 对齐）

最新软件端的页面与数据面：

- **第一批（软件端页面直接需要）**：`Member`、`FoodCatalog`、`ShoppingListItem`、`Notification`、`ConsumptionLog`、`Device`、`Container`，并给 `FoodItem`/`ScanLog` 扩 `recordedBy`/`recordMethod`/`keepDays`/`storage`/`label` 字段；

### 3.5 硬件交互侧（数据库 / 后端同样要考虑）

| 硬件行为 | 后端 / 数据库设计 |
|---|---|
| 设备在线状态（Wi-Fi 链路） | `Device` 表（deviceId、name、firmwareVersion、memberId、lastSeenAt）；新增 `POST /api/device/heartbeat` 更新最后在线（>5 分钟未上报视为离线） |
| 扫描上报（放入/取出） | `POST /api/scan`（已有）：multipart → 识别 → `FoodItem`/`ScanLog`；响应加 `keepDays`（固件解析器忽略未知字段，兼容） |
| 待机屏显示临期 / 过期提醒 | `GET /api/device/state?deviceId=`：返回该设备视角的临期/过期列表 + 最近识别结果（固件可离线缓存的兜底数据） |
| 设备本地库存计数与云端一致性 | **以后端为准**：`/api/scan` 响应可附 `stockTotal`（该设备当前总件数）；固件本地 KV 仅作离线兜底展示 |
| 温度传感器（DS18B20，可选） | 新增 `TemperatureLog`（deviceId、tempC、readAt），由心跳带上或独立上报；异常触达 `ReminderRecord(type=temperature)` |
| 设备诊断 / UART 日志 | 新增 `DeviceLog`（deviceId、event、msg、createdAt）；固件 `[XZD]` 事件（LINK_UP/SCAN_START/SCAN_OK/LOW_CONF/OFFLINE）可经心跳附带上报，便于路演展示“设备在线记录” |
| 设备与成员绑定 | `Device.memberId`：设备归属成员，扫描默认录入人 = 绑定成员 |
| 安全说明 | 固件 TLS no-verify、无鉴权 → `/api/scan`、`/api/device/*` 原型阶段公开；上线前需加设备级鉴权（如设备 Token） |

## 6. 用户注册与登录（2026-08-18 新增）

站点已补齐完整账号体系：注册 → 自动登录（JWT Session Cookie）→ 登录 / 登出 / 会话查询。
注册用户默认为 `role=user` 的普通成员；管理员角色保留（`User.role=admin`），原型阶段无管理后台页面。

### 数据库

- 表：`User`（Prisma / SQLite，已有，无需迁移）：
  `id`、`name`、`email`（唯一）、`passwordHash`（bcrypt 10 轮）、`role`（admin | user）、`active`、`createdAt`；
- 会话：JWT（HS256，7 天有效期），存 `httpOnly + SameSite=Lax` Cookie（生产环境自动加 `Secure`）；
- 密码不落明文，注册 / 登录 / 修改密码均走 `bcryptjs` 哈希。

### 接口契约

| 接口 | 说明 | 入参 | 响应 |
|---|---|---|---|
| `POST /api/auth/register` | 公开注册，成功后直接写入会话（自动登录） | `{ name, email, password }` | 201 `{ user }` + Set-Cookie；400 参数不合法；409 邮箱已注册 |
| `POST /api/auth/login` | 登录 | `{ email, password }` | 200 `{ user }` + Set-Cookie；401 邮箱或密码错误 |
| `GET /api/auth/me` | 查询当前会话 | 无（带 Cookie） | 200 `{ user }` 或 `{ user: null }` |
| `POST /api/auth/logout` | 登出（清除会话 Cookie） | 无 | 200 `{ ok: true }` |
| `POST /api/auth/password` | 修改密码（需登录） | `{ oldPassword, newPassword }` | 200 `{ ok: true }`；400 旧密码错误 / 新密码过短 |

注册校验规则：姓名 1–50 字；邮箱需为有效格式（自动转小写、去空格）；密码至少 6 位；邮箱已存在返回 409。

### 页面

- 食刻 H5（`/shike-h5.html`）：已内置登录 / 注册门禁页，打开先校验会话（`/api/auth/me`），未登录显示登录 / 注册切换表单；
  注册 / 登录成功自动进入应用，「我的」页顶部有账号卡片（显示姓名邮箱 + 退出登录）；
  后端不可达时提供「先逛逛（游客模式）」入口，不影响离线演示。

### 部署说明

数据库表结构未变（`User` 表已存在），服务器上 `docker compose up -d --build` 重启即可；
`AUTH_SECRET` 已在 `.env`，生产环境请用 `openssl rand -hex 32` 生成并保持稳定（用于签发/校验会话 JWT）。

## 9. 设备指令下发（平板 → 内模组 · 待后端新增）

> 与设计基线 §3.1 对齐：外置平板触屏【放入/取出】→ 指令下发内模组 → 扫码。
> 状态：✅ **已实现（2026-08-23，后端 commit 28a89c3）**；接口均需设备 `X-Device-Token` 鉴权。

| 接口 | 说明 |
|---|---|
| `POST /api/device/task` | 平板选择动作后调用：`{ "deviceId": "shike-xiao-001", "action": "in"\|"out" }`；云端保存该设备"当前动作"（持久化，直到下次修改）；响应 `{code:0}` |
| `GET /api/device/task?deviceId=shike-xiao-001` | 内模组扫码前调用：返回 `{"code":0,"data":{"action":"in"\|"out"\|null}}`；无记录时 `action=null`，固件默认 in |

### 9.1 内模组结果同步（平板轮询）

`GET /api/scan/latest?deviceId=shike-xiao-001`（内模组 Token 鉴权）——外置平板在等待扫码页每 2–3s 轮询：

```json
{"code":0,"data":{
  "id":"...","name":"光明鲜牛奶","action":"in",
  "scannedAt":"2026-08-23T04:00:00.000Z",
  "expiryDate":"2026-08-25","daysLeft":2,
  "suggestedContainer":"冰箱","stockTotal":12
} | null}
```

- 无记录 / 无事件时 `data=null`；平板显示"等待内模组扫码"；
- `id` 供后续去重（当前固件取到即显示，重复轮询只在等待态发生，可接受）。

### 9.2 汇总待确认与确认

`GET /api/summary/pending?deviceId=xzd-t5e1-001`（平板 Token 鉴权）——返回最近一个 `status=pending` 的关门结算批次：

```json
{"code":0,"data":{
  "batch":{"id":"...","inCount":3,"outCount":1,"midOutCount":1,"unknownCount":2,"createdAt":"..."},
  "items":[{"id":"...","kind":"unknown","name":null,"status":"pending","note":null}]
} | null}
```

`POST /api/summary/confirm`（平板 Token 鉴权）：

```json
{"batchId":"...", "items":[{"id":"...","status":"confirmed"|"ignored"}]}
```

- `items` 缺省 = 批次整体确认；提供则逐条更新，全部处理完后批次 `pending → confirmed`；
- 批次数据由**云端自动窗口结算**产生（见 §9.3），内模组补充事件见 §9.4。

### 9.3 关门结算批次 · 云端自动窗口结算（2026-08-23 已实现，后端 commit 7838a89）

- **窗口定义**：同一设备 `ScanLog` 按 `scannedAt` 排序，相邻两条间隔 ≤ **10 分钟**（`WINDOW_GAP_MS`，可配置；EXP-02 实测开门平均 <20s）视为同一开门窗口；
- **结算规则**：窗口**闭合**（最后一条距当前 >10 分钟）后自动生成 `SummaryBatch`：
  - `inCount` / `outCount` 按窗口内 `action` 统计；每条扫码生成一个 `SummaryItem`（kind=in/out）；
  - `midOutCount` / `unknownCount` 默认 0，由内模组 `POST /api/summary/submit` 补充（§9.4）；
  - 结算后 `ScanLog.batchId` 标记，幂等不重复归批；
- **结算时机**（ADR-005 延迟确认，不追求关门即时）：
  1. 每次 `/api/scan` 入账后自动检查；
  2. `GET /api/summary/pending` 查询前惰性结算；
  3. 内模组 `submit` 可立即结算。

### 9.4 内模组补充事件（关门结算上报，契约已定 · 固件端待接）

`POST /api/summary/submit`（内模组 Token 鉴权）：

```json
{
  "deviceId": "shike-xiao-001",
  "requestId": "win-20260823-001",
  "events": [
    {"action": "midout", "name": "光明鲜牛奶"},
    {"action": "unknown", "name": null}
  ]
}
```

- `events` 提供未识别 / 中途取出等扫码日志没有的信息，并入当前窗口并**立即结算**；
- `events` 缺省：仅触发立即结算（把打开的窗口闭合）；
- 响应 `{"code":0,"data":{"settled":true}}`；`requestId` 幂等去重；
- 内模组固件（05/06）接入后，关门时调一次即可让平板即时看到批次。

分工：

- 平板端（T5-E1 app_xzd.c）：待机页【放入】【取出】按钮 → `POST /api/device/task`（带 `X-Device-Token`）；
- 内模组（05 完整链路）：已按此契约实现 `fetchPendingAction()`，按下扫码键时先 GET 再上传；
- 语义：动作持续有效直到平板再次下发（支持"连续扫多件同一动作"）；清空动作可选（平板再发一次或后端提供删除）。
